# Стандарты исходников расширения

Дата сверки: **2026-10-15**. Это переносимая адаптация подтверждённых правил QRKO для самостоятельного публичного расширения. Она не требует приватного реестра, соседних checkout или серверной части BudetOffer и не заявляет соответствие недоступному skill `qrko-conventions`.

## Основания

Ниже указаны пути в проверенном проекте QRKO, а не файлы этого репозитория.

| Источник QRKO                                                                                    | Что перенесено сюда                                                                                                                                                                    |
| ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `frontend/libraries/package.json`, команда `format`                                              | Prettier 3.9.9; стандартное форматирование отдельно от проверки корректности. Локальная конфигурация codegen не распространяется на всё приложение.                                    |
| `frontend/libraries/tsconfig.base.json`, аналогичные конфигурации public и admin                 | `strict`, `noUnusedLocals`, `noUnusedParameters`, `noFallthroughCasesInSwitch`.                                                                                                        |
| `frontend/admin/oxlint.json`                                                                     | Запрет вложенных тернарных операторов; правила React Hooks и проверка зависимостей effects. В этом репозитории все эти проверки останавливают CI при ошибке.                           |
| `frontend/public/modules/prime-public/AGENTS.md` и `frontend/admin/scripts/check-boundaries.mjs` | Разделение ответственности интерфейса, публичные точки входа и отдельная проверка границ импортов. Astro SSR-правила относятся к веб-приложению QRKO и не переносятся в Chrome worker. |

Инструмент проверки здесь — ESLint 9 с neostandard и React Hooks, а не обязательное копирование QRKO Nx/oxlint/pnpm. Версии зависимостей фиксируются в `package-lock.json`; сборка использует публичный npm.

## Форматирование и читаемость

- Prettier 3.9.9 задаёт единый формат: отступ 2 пробела, ширина 80, точки с запятой, двойные кавычки, trailing commas, LF. Эти значения записаны в [`.prettierrc.json`](../.prettierrc.json).
- `npm run format` исправляет формат; `npm run format:check` проверяет его без записи. ESLint не становится вторым форматтером.
- Сложные состояния оформляются через именованные вычисления, ранние возвраты или `switch`. Вложенные тернарные операторы запрещены.
- Обработчики действий с проверками и побочными эффектами получают имена; JSX описывает интерфейс. Стиль объявления `function` или arrow сам по себе не является универсальным запретом.

## Типы и внешние данные

- Собственные runtime-модули, popup и сборочные скрипты пишутся на TypeScript/TSX. Используется `import type`; runtime-импорты исходных модулей расширения содержат `.ts`.
- Команды и результаты протокола — дискриминированные объединения. Поля, необходимые конкретной команде, обязательны именно для неё.
- JSON, сообщения Chrome, storage и данные HH проверяются на границе как `unknown`. Типы не заменяют runtime-проверки аккаунта, владельца, срока задания и серверного разрешения.
- Запрещены явный `any`, небезопасный тип `Function`, `@ts-ignore`, `@ts-nocheck`, `@ts-expect-error` и inline-отключения ESLint. Не исправляйте ошибку приведением непроверенного значения к ожидаемому контракту.
- `npm run check` отдельно проверяет runtime, popup, Node-инструменты, **Node- и UI-тесты**, затем границы импортов. Общая строгая база находится в [`tsconfig.base.json`](../apps/chrome-companion/tsconfig.base.json).

## Архитектура и окружения

UI следует направлению `app → pages → widgets → features → entities → shared`. Неиспользуемые слои не создаются. Логика одного popup остаётся в `pages/companion-popup`; внешние потребители используют его `index.ts`. Общий UI не импортирует страницы и не содержит workflow подключения.

Chrome worker, код страницы HH, popup и Node-сборка имеют разные точки входа и TypeScript-конфигурации. Node API не должны попадать в устанавливаемый код. Runtime- и popup-проверки не получают глобальные типы Node; Node-инструменты проверяются отдельно. Тесты имеют собственную конфигурацию и разрешённые тестовые окружения.

`npm run check:boundaries` проверяет эти границы и vendored-исходники. Это конкретный локальный gate, а не заявление о полной автоматической проверке всей методологии FSD.

Общий контракт EWANS разрешён через единственную точку входа `packages/ewans/src/index.ts`. Проверка требует, чтобы этот модуль не имел импортов. Сборщик включает только этот файл дополнительно к runtime расширения, переносит его в `shared/ewans.js` и меняет только спецификаторы импортов. Остальные пакеты и серверные исходники недоступны runtime. [Устройство EWANS](ewans.md).

Функции, передаваемые в `chrome.scripting.executeScript`, Chrome сериализует без замыкания модуля. Поэтому их небольшие runtime-guards могут намеренно повторяться внутри функции. Нельзя выносить такой guard в импорт и считать прямой unit-вызов достаточной проверкой: тест должен выполнять скомпилированную сериализованную функцию.

## UIKit и происхождение файлов

Используются имеющиеся UI-примитивы, UIKit и токены. Изменение структуры кода само по себе не требует менять внешний вид.

Файлы из `vendor`, перечисленные в [`vendor/provenance.json`](../vendor/provenance.json), сохраняются побайтно. Они исключены из автоматического форматирования и lint; это не разрешение менять их без проверки. Обновление источника требует явного пересмотра версии, состава, SHA-256 и лицензий. Сборочные адаптеры `package.json` отделены от зафиксированных оригинальных файлов.

## Проверки перед изменением релиза

```bash
npm run format:check
npm run lint
npm run check
npm test
npm run build
```

Проверка типов тестов входит в `check`; узкие команды — `check:runtime`, `check:popup`, `check:node`, `check:tests`, `check:boundaries`. Тесты должны проверять поведение и ограничения безопасности, использовать синтетические данные и не требовать пользовательского аккаунта.

Готовность релиза подтверждается результатами этих проверок, сканированием секретов и сравнением ZIP со сборкой из конкретного коммита. Инструкции: [самостоятельная сборка](source.md), [публикация версии](releasing.md).
